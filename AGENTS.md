# Agent Workflow

Before acting, read the shared benchmark rules, starting from
`https://github.com/tensor4all/tensor4all-agent-rules/blob/main/rules/benchmark/measurement.md`
(bind yourself off the measured cores, one measurement at a time, a discarded run stays
discarded) and `.../rules/benchmark/index.md` for the rest (evidence, tables). Fallback:
`../tensor4all-agent-rules/rules/benchmark/`. Load only the files your task touches.


## Source of truth for numbers

Tracked result pages live under `result/<profile>/<suite>/<revision>.md`, one page per measured
`(suite, hardware profile, revision)`, and are generated from the raw run under
`data/results/<profile>/<suite>/<timestamp>/`. Do not duplicate result tables into `README.md` or
into docs. Historical reports are not maintained; use git history.

`result/INDEX.md` is generated by `scripts/gen_index.py`. Never edit it by hand.

## Merging a candidate into `tlinalg-rs` main

The order of operations - preconditions, the observer pin checklist, the target/guard pair, the
control decision (the unchanged row's median), and what a merge does and does not prove - is
[docs/merge-procedure.md](docs/merge-procedure.md), which instantiates the shared procedure in
`campaign-toolkit/docs/merge-procedure.md`. Read it before merging anything. A suite-wide "no
regression" claim belongs to the periodic full declared-suite run, never to a merge.

## Every published number carries its revision and its vendor

A measurement without the commit it was taken at is not evidence. `run.yaml` records the measured
checkout's path, commit, dirty state and features, the harness commit, the host, the thread
environment, the CPU set used at each thread count, the vendor library the LAPACK arm was linked
against (its version, build configuration and the kernel its runtime dispatched to), the guard
logs, and the timing policy. `scripts/validate_run.py` refuses to accept a manifest whose commit
does not resolve, or whose declared engines include a vendor arm with no vendor identity. If you
quote a number anywhere, quote its commit with it.

## One vendor arm per run

The vendor row's name is not chosen by whoever writes the row: the harness derives it from the
library the binary linked, so it emits `lapack-openblas` or `lapack-mkl` because that is what it
loaded. The two are mutually exclusive in one process -- they define the same symbols -- so
`--vendor` selects an arm at build time and an arm is a whole run, with its own manifest, its own
page and its own faer rows. Do not merge two arms into one manifest or one page: `vendor`
describes the one library that produced those numbers, and a manifest naming two would describe
neither. The recorder refuses a run whose harness reports a vendor other than the arm requested,
and the validator refuses a manifest whose vendor is not the one its engines name. MKL reports no
dispatched-kernel name and no processor count; its manifest leaves both empty rather than infer
them, and the page says so.

## What the `openblas` arm actually is on this campaign's host

Four properties of the arm change how its rows read, and none of them is visible in a page. Each
was found by reading what a recorded build did, not by assuming; re-check them when the arm or
the machine moves.

- **It is not a Fortran LAPACK build.** `openblas-build` falls back to BLAS plus the
  f2c-converted LAPACK when it finds no Fortran compiler, and says so:
  `cargo:warning=OpenBLAS: Detecting fortran compiler failed. Only BLAS and f2c-converted LAPACK
  are compiled.` The development host has no `gfortran`, so every `lapack-openblas` row recorded
  so far was measured against that fallback. Installing a Fortran compiler changes which LAPACK
  the row measures — a library change with its own A/A, not a build detail. Read it from
  `target/tlinalg-rev/<rev>-openblas/*/build/openblas-src-*/output`.
- **`DYNAMIC_ARCH=1` dispatches to `Cooperlake`** on the Zen 5 development host, an Intel AVX-512
  target, because the OpenBLAS in use names no Zen 5 kernel. The manifest records the kernel it
  dispatched to (`vendor.corename`); a row from this machine is a Cooperlake row, and the page
  must not let a reader infer a Zen-tuned library.
- **The OpenBLAS version is a constant in the build crate, not a property of the host.**
  `openblas-src` pulls `openblas-build`, whose `OPENBLAS_VERSION` is `0.3.32` for the revision in
  `Cargo.lock`; it has no environment override and the tarball is fetched without a checksum.
  Moving the arm to a newer OpenBLAS is a dependency bump in `tlinalg-rs`, recorded by the usual
  pin — not something the machine or an image can choose.
- **The build is wrapped by `kache` on the development host.** `~/.cargo/config.toml` sets
  `rustc-wrapper = "kache"` and `CC = "kache cc"`; `build_for_tlinalg_rev.sh` clears
  `RUSTC_WRAPPER` but not `CC`, and no manifest field records either. A cache wrapper should not
  change the object it passes through, but a reader of a page cannot tell from the page which
  compiler invocation produced the binary.

## Timing discipline

One measurement at a time, and **no build while a measurement is running**. `scripts/record_run.py`
holds one campaign-level lock across build, verify and timing for exactly this reason; a lock inside
a per-revision target directory would let a second recorder build another revision during a
measurement. Every timing goes through the protocol script of the *measured* checkout
(`benchmarks/scripts/pinned.sh`), which pins the cores and checks that those cores **and their SMT
siblings** were idle before and after; a run spoiled by other load is discarded, not published.

Priming is **time-based** (at least 0.5 s of wall time per arm) and identical on every arm. A fixed
call count is not a substitute: after an idle gate this host reads low for the first second or two
of sustained AVX-512 work, which is large enough to be mistaken for a kernel defect. The reference
harness in `tprims-rs` records 500 ms while performing a single warm-up call; do not repeat that
mistake, and do not treat a manifest constant as evidence that priming happened.

A thread budget is declared, not inherited. The harness sets the vendor library's own thread count
from the row's budget and reads it back before measuring, and the recorder removes the ambient
thread variables from the measured process's environment.

Correctness precedes timing. `tlbench verify` must report a clean grid for every population and
thread count before any timing pass; the recorder enforces this and publishes nothing otherwise.

## Coverage is data, not an apology

The campaign is not run in full on every profile for every commit. A partial run is legitimate: it
is recorded, it is marked `partial` in the index, and it never displaces a full-coverage report. Do
not describe a partial run as if it covered the suite, and do not infer "no regression" for a
population the run did not contain. Cases a provider cannot take are recorded as `skipped` in the
run's own CSV and in `run_spec.populations[].skipped`, not silently dropped.
